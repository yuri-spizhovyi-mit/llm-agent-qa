# 10 · Presenting AI-QA work

*Milestone 10. Files: `README.md`, `docs/requirements.csv`, `docs/rtm.md` (from
`scripts/rtm.py`), `scripts/evidence_pack.py`, `.github/workflows/release.yml`. Tests: ENV-05,
ENV-06.*

## 1. The reader has two minutes

A reviewer opening this repo wants three answers, in this order:
1. **What is it?** One sentence: an agent that can move money, and the suite that proves it's safe
   and useful.
2. **Does it find anything?** Findings, with evidence: a real hole (F-06), and bugs in the
   measurement itself (F-09, F-10, F-13).
3. **Can I trust the numbers?** Intervals, the run each number came from, what it cost, and what
   wasn't measured.

The README is built in that order: problem, what was built, what it found, the numbers, how to
check them, and the honest limits. Everything else is one link away.

## 2. Lead with findings, not features

"An LLM judge with bias probes" is a feature. "The judge passed calibration, then failed 87 of 93
true answers, and here is why" is a finding. Findings show that the suite works: it caught
something real. And they show judgment: you knew it was wrong although it looked fine.

Good findings to lead with:
- **A real defect in the system under test:** the duplicate invoice paid twice (F-06).
- **A defect in the measurement:** a judge with incomplete facts (F-10), an outage counted as
  safety (F-13). In AI QA, these are often the most valuable, because a broken eval looks exactly
  like good news.
- **A root cause shared by several symptoms:** the payment limit the agent can't see (F-11).

## 3. Numbers with their uncertainty

Every rate gets its interval, its sample size, its source run and its cost. "91 of 93 (95% CI
92–99%), run 43140844044, about $10" can be checked. "98% accurate" can't. And say what a zero
means: 0 of 48 attempted attacks means the true rate is below about 7%, not that it's 0.

## 4. Traceability: from requirement to test, generated

A requirements traceability matrix (RTM) answers "what does this suite promise, and which test
proves each promise?"

- **The catalogue** (`docs/requirements.csv`): 43 requirements, each with an area and a risk
  level, written as checkable statements.
- **The links:** each test names its requirement with `@pytest.mark.req("GATE-02")`.
- **The matrix** (`docs/rtm.md`) is generated by `scripts/rtm.py` from the tests' own code, never
  kept by hand. ENV-05 fails if a requirement loses its last test, a test cites an unknown ID or
  none, or the matrix is stale.

A hand-kept matrix is wrong within a month. A generated, checked one can't be.

## 5. The evidence pack

A release isn't only a tag: it ships the evidence that it passed. `release.yml`, on a `v*` tag:
1. runs the whole suite (no API key);
2. replays the 93 real Claude answers;
3. builds the pack with `scripts/evidence_pack.py`, and attaches it to the GitHub release.

The script **refuses to build** if:
- any test failed;
- the traceability has a gap;
- the replayed answers no longer equal the stored baseline.

So a pack exists only for a release that passed. It holds:
- the raw results;
- the eval report, findings, decisions, the matrix and the baselines;
- the live runs' own reports;
- an `EVIDENCE.md` summary;
- `SHA256SUMS` for every file, so anyone can check nothing was edited afterwards.

## 6. Say what you didn't do

This project ran out of API credits before three measurements: the second judge's live
calibration, a worse prompt blocked on the real model, and the candidate fix for F-11. The README
says so, and decisions GATE-D6 and AGT-D4 record what each would take. A reviewer trusts the rest
more for it. An unlisted gap, found later, costs more trust than the gap itself.

## 7. Interview questions

**"Walk me through this project in two minutes."**
> An accounts-payable agent on Claude that proposes payments on a real local chain, and the suite
> around it. 31 golden tasks scored on chain state, with intervals; a calibrated LLM judge; a
> two-level red team; a statistical regression gate. Real results: 91 of 93, and no attack
> executed. The interesting part is what it caught. A duplicate invoice paid twice, fixed in the
> policy. And three bugs in the measurement itself: a judge with incomplete facts, an outage that
> read as safety, and a CI step that called a crash a pass.

**"How do you know your test suite covers the requirements?"**
> A generated traceability matrix. Each requirement is a checkable statement, each test names the
> requirement it proves, and CI fails on an untested requirement, an unknown ID or a stale matrix.

**"What would you do differently?"**
> Keep transcripts of every paid trial from day one: the red team's first real attempt left no
> words (F-14). Calibrate the judge on real answers before trusting it, not after (F-10). And budget
> API credits for the measurements that matter most: the fix I couldn't measure is the gap I'd
> close first.

**"What does a release of a test suite even mean?"**
> A tagged state of the suite with the evidence that it passed: the results, the traceability, the
> baselines and the reports, checksummed, and refused if anything failed.
