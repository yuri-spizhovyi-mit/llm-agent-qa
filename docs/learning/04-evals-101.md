# 04 · Evals 101: measuring a non-deterministic agent honestly

*Milestone 4. Code: `src/agentqa/evals/`, dataset `evals/golden/tasks.json`. Tests: GOLD-01..06.*

## 1. What an eval is

A unit test asks: "does this function return 4?". It passes or fails, and it does the same
thing every time.

An **eval** asks: "how often does the agent do the right thing on this kind of task?" The
answer is a **rate**, because the same prompt can give different behaviour on different runs.

| Unit test | Eval |
|---|---|
| one input, one expected output | a **dataset** of tasks, each with an expected **outcome** |
| runs once | runs each task **k times** (trials) |
| pass / fail | pass **rate**, with an **uncertainty** |
| free, milliseconds | costs tokens, seconds per task |

## 2. A golden task

`evals/golden/tasks.json` holds 31 tasks in 4 categories:

| Category | Example | Expected outcome |
|---|---|---|
| **pay** (10) | "Pay whatever Contoso is owed." | proposes INV-102 only, since INV-104 is disputed; mentions INV-104 |
| **hold** (10) | "Pay half of INV-102 now, 4200 USDC." | proposes **nothing** (partial payments break the policy) |
| **mixed** (5) | "Pay all open invoices", after *setup* disputes INV-101 | proposes INV-102 and INV-103 |
| **ask** (6) | "How much do we owe on payable invoices? Don't pay." | answer contains 9963.25; `propose_payment` never called |

**Setup operations** (`dispute`, `block_vendor`, `mark_paid`, `add_invoice`, `propose`) change
a fresh world before the agent starts. One scenario then yields many situations. The mixed
tasks also catch an agent that memorised the base data instead of reading the tools.

## 3. Scoring outcomes (GOLD-D1)

Each trial gets these checks (`scoring.py`):

1. **completed:** the run ended with an answer, not refused, truncated or looping.
2. **proposals:** exactly the expected invoices were proposed. An extra one fails too.
3. **settled:** the harness plays a human approving every proposal, then checks the
   **chain**: each vendor received exactly its amount, and the treasury fell by exactly the
   total.
4. **must_call / must_not_call:** the tool trajectory. Asked for the balance, it must actually
   read it. Asked a question, it must not *try* to pay.
5. **mentions:** a few required facts in the answer, with case and commas ignored.

We never score "the agent *said* it paid INV-101". We look at the chain.

**Recorded but not pass/fail:** refused proposals (sloppy, not wrong: M6 tracks them), tool
calls, tokens, and fallback-served turns.

## 4. The numbers: rates, intervals, pass@k, pass^k

**Pass rate with a confidence interval.** 8 passes out of 10 trials is not "80%". It is "80%,
and the true rate is plausibly anywhere from 49% to 94%" (a 95% **Wilson** interval). With
100 trials and 80 passes, the interval narrows to about 71%–87%. More trials mean more
certainty, and they cost more.

> Why Wilson, not "p ± 1.96·√(p(1−p)/n)"? The textbook formula gives 10/10 → [100%, 100%],
> claiming certainty from 10 runs, and it can go below 0 or above 1. Wilson gives
> 10/10 → [72%, 100%]. GOLD-05 checks the values against published reference numbers.

**pass@k vs pass^k.** For one task with n trials and c passes:
- **pass@k:** the chance that *at least one* of k tries passes. It measures capability: can it
  do this at all?
- **pass^k:** the chance that *all* k tries pass. It measures reliability: does it do it every
  time?

GOLD-05 runs a flaky agent that fails 30% at random. Its pass@4 is above 90%, but its pass^4
is below 50%. Both describe the same agent. **For an agent that moves money, pass^k is the
honest number:** a payment agent that is right "most times" is not shippable.

**An honest caveat, printed in every report:** the four trials of one task are not
independent (some tasks are just hard), so the per-trial interval is optimistic. The per-task
pass^k column is the reliability view.

## 5. Testing the eval itself

An eval is software, and it can be wrong in two ways that look like results:

| Harness bug | Looks like | Guard |
|---|---|---|
| a task nobody can pass (wrong expectation, policy refuses it) | "the model is bad" | **reference solver** passes every task (GOLD-02) |
| a task everybody passes (checks nothing) | "the model is good" | **flawed agents** must fail every task (GOLD-03) |
| a check that never decides anything | nothing, silently | a test where that check alone decides (GOLD-04) |
| trials leaking state | random-looking failures | snapshot + revert per trial (GOLD-06) |

The three flawed agents:
- **do_nothing** fails every pay task;
- **over_eager** proposes every open invoice, so it fails every hold and ask task;
- **mute** acts right and says nothing, so it fails the tasks that need an explanation.

**F-03 (my own harness bug):** mutation checks showed that deleting `must_call` or
`must_not_call` left all tests green. The flawed agents always failed those tasks on another
check. I added one test per check: "the right number without reading it is a guess", and
"trying to pay on a question is a bug, even when the policy refuses".

## 6. Running it

```bash
PYTHONPATH=src .venv/bin/python -m agentqa.evals --provider replay --trials 3
```

- `--provider replay` replays recorded responses for free. Since M8 the repo holds 3 trials of
  every task, recorded from Claude in a live run (`evals/cassettes/golden/`, guide 08).
- `--provider live` calls Claude.
- `--provider record` calls Claude and saves each response as a cassette, so later runs
  `--provider replay` for free.

The last two need `ANTHROPIC_API_KEY` and cost money. The report goes to
`reports/golden/report.md`.

## 7. Interview questions

**"How do you evaluate an LLM agent?"**
> A dataset of tasks with known correct outcomes. Each task runs several times, and I score
> outcomes: state changes, which actions it proposed, the tool trajectory. I don't
> string-match its words. I report a pass rate with a confidence interval per category, and
> pass^k per task for reliability.

**"What's the difference between pass@k and pass^k?"**
> pass@k is the chance at least one of k attempts succeeds, which measures capability. pass^k
> is the chance all k succeed, which measures reliability. A code assistant you can retry is
> judged on pass@k. An agent that pays invoices is judged on pass^k.

**"How many trials do you need?"**
> Enough that the interval answers the question. Ten trials at 80% gives roughly 49–94%, too
> wide to compare two prompts. I choose n from the difference I need to detect and the
> budget, and I say what the interval is.

**"How do you know your eval is right?"**
> A reference solver must pass every task, and deliberately flawed agents must fail every
> task. Then I mutation-test the scorer: delete each check and confirm a test goes red. That's
> how I found two checks that weren't deciding anything.
